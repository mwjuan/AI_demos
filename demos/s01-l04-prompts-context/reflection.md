## 能运行

- 消息构造测试是否通过？通过，本课共 14 个自动测试通过。
- 单变量提示词实验得到了什么差异？直接解释组使用技术化说明；比喻组使用“乐高小块”向小学生解释。两组都是 59 个字符。
- 结构化 JSON 是否每次都能解析？真实结构化实验成功解析；但应用仍保留语法和字段校验，不能假设每次都会成功。

## 能解释

1. `system`、`user`、`assistant` 分别承担什么职责？`system` 规定任务和风格，`user` 表示用户问题，`assistant` 表示模型此前的回答。
2. 为什么对话历史会影响下一轮回答？历史消息被应用再次发送给模型，成为当前上下文的一部分。
3. 为什么上下文不等于永久记忆？模型只能看到本次请求实际提供的消息、文件或工具结果；被删除且没有摘要的信息不能可靠使用。
4. 为什么提示词实验一次只改变一个变量？避免把随机差异或其他条件变化误认为某个提示词的效果；每组还应尽量多次运行。
5. 为什么不能仅凭“看起来像 JSON”就相信模型输出？需要分别验证 JSON 语法、字段结构和内容事实；形式正确的内容仍可能是错的。

## 能修改

- 我增加或修改的提示词变量：把模糊的“简洁”改成“不超过 80 个汉字”，并明确问题是大语言模型 Token，而非登录认证 Token。
- 我保持不变的条件：模型、用户问题、长度限制和运行方式保持一致，只改变直接解释与生活化比喻的风格。
- 我观察到的结果：两组均为 59 个字符，比喻组出现了“乐高小块”，风格差异明显。
- 我的结论：明确的领域和可检查的约束比模糊要求更可靠；一次结果仍会受到模型随机性影响。

## 失败样本

- 原始模型输出：第一次实验把 Token 解释为登录认证令牌，而不是大模型文本 Token。
- 解析错误：没有 JSON 解析错误；这是语义歧义导致的内容偏离。
- 我的猜测：用户问题“解释 Token”缺少领域，上下文不足。
- 修复方式：改为“解释大语言模型处理文本时的 Token，不要讨论登录认证 Token”，并继续对结构化结果做 Python 校验。
